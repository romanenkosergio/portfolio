# sud

Для случаев, когда Claude со всем соглашается. Вместо одного вежливого ответа идея идёт под суд:
прокурор строит обвинение, адвокат строит защиту, а присяжные из Claude, которые друг друга не видят,
голосуют. Ты секретарь суда. Ты ничего не доказываешь, не голосуешь и не смягчаешь вердикт.

Что пользователь написал после `/sud`: `$ARGUMENTS`

Если там пусто или стоит заглушка, возьми дело из разговора: идею, план или утверждение, о которых
пользователь последними просил мнение.

## Портфолио (настройка под проект)

Скилл адаптирован под личный сайт-портфолио (Next.js, FSD) фронтенд-разработчика:

- Присяжные в `jurors.json` — те, кто читает портфолио и кто его оценивает: технический рекрутер,
  нанимающий менеджер, тимлид фронтенда на тех-интервью, заказчик-фрилансер, дизайнер, SEO-специалист,
  эксперт по доступности, эксперт по производительности, джун, который ищет пример, скептичный
  коллега, HR из продуктовой компании, основатель стартапа.
- Файл дела начинается с блока «О продукте» из `project-context.md` (в папке скилла) без изменений,
  затем идёт само дело. Факты для дела бери из `docs/` (`PLAN.md`, `HANDOFF.md`, `DECISIONS.md` с
  номерами `D###`), из кода и из слов владельца; номера решений указывай. Если дело про то, как сайт
  выглядит, приложи итог агента `visual-checker` (его отчёт, а не свои выводы).
- Темы для полного прогона («прогони всё»): первое впечатление и главная; что показано о проектах и
  опыте; контакты и призыв к действию; текст и тон; дизайн и мобильная версия; SEO и метаданные;
  доступность; производительность; что выделяет среди других портфолио.
- Пакетный прогон: по делу на тему, каждое в своей папке — перед каждой командой
  `SUD_ROOT=.sud/<тема>`. Суды идут параллельно: одна фаза всех дел за раз. По умолчанию `--quick`.
- Речи и присяжные — `model: "sonnet"` в вызове Agent, судья — модель по умолчанию.
- После вердиктов координатор сводит «Условия оправдания» всех дел в одну таблицу в
  `docs/sud-<дата>.md`; решает владелец, новые `D###` записывает координатор, пункты — в `docs/PLAN.md`.
- `.sud/` не коммитится.

## Инструмент

Весь учёт идёт через `sud.py` в папке этого скилла:

```bash
python3 "${CLAUDE_SKILL_DIR}/sud.py" <команда>
```

Дальше `SUD` значит ровно эту команду. Если путь остался нераскрытым, возьми «Base directory for
this skill», который Claude Code напечатал в начале скилла. Состояние лежит в
`.sud/<запуск>/state.json` в текущей папке, и каждая команда после `init` находит его через
`.sud/LATEST`.

## Шаг 1: прикинь размер

Вычитай флаги из запроса. Всё, что не флаг, это дело.

| флаг | что значит |
| --- | --- |
| `--jury N` | N присяжных, от 3 до 12. По умолчанию 12. |
| `--quick` | 6 присяжных. |
| `--seed S` | Фиксирует, какие присяжные сядут в меньший состав. По умолчанию случайно, значение записывается. |

Запусти `SUD plan` с теми же флагами и одной строкой скажи пользователю, какой будет суд, например:
«12 присяжных, 17 вызовов суб-агентов». Потом начинай. Если скилл сработал сам (пользователь суд не
просил), сначала один раз спроси и предложи `--quick`.

Суб-агенты пишут в `.sud/` в текущей папке. В обычном режиме разрешений это одно подтверждение на
каждый файл. Предложи режим accept-edits (Shift+Tab) на время суда. Настройки пользователя сам не меняй.

## Шаг 2: напиши файл дела

**Суб-агенты не видят этот разговор.** Прокурор, адвокат, каждый присяжный и судья знают только то,
что лежит в файле дела, поэтому пиши `.sud/case.md` так, чтобы он читался сам по себе:

- Первая строка: дело в одном предложении, по возможности словами пользователя («Бросить работу
  медсестры, чтобы целиком заняться продажей свечей ручной работы на Etsy»).
- Дальше всё, что пользователь рассказал и что важно: цифры, аудитория, бюджет, сроки, что уже
  пробовал, ограничения.
- Не добавляй фактов, которых пользователь не называл, и не вписывай своё мнение об идее. Файл дела,
  который клонит в одну сторону, решает суд ещё до его начала.

## Шаг 3: открой суд

```bash
SUD init --case-file .sud/case.md [--jury N | --quick] [--seed S]
```

## Шаг 4: суд

Всегда веди его через `SUD next`. Команда читает файлы на диске и говорит, какая фаза следующая и какую
команду запускать. Фазы идут в таком порядке: `opening` (вступительные речи), `rebuttal` (ответные речи),
`jury` (присяжные), `judge` (судья).

Каждая фаза устроена одинаково:

1. `SUD prompts <фаза>` пишет по одному заданию на каждую работу и перечисляет работы, которые ещё
   надо сделать, волнами.
2. Запускай **по одной волне за раз**: одно сообщение, в нём по одному вызову инструмента Agent на
   каждую работу волны (в старых версиях Claude Code инструмент называется Task). Каждый вызов:
   - `subagent_type`: `general-purpose`
   - `description`: `sud <id работы>`
   - `prompt`: `Прочитай <путь к заданию> и выполни его точно. Это всё твоё задание.`

   Дождись ответов от всех агентов волны и только потом запускай следующую.
3. После последней волны запусти `SUD next`. Если какого-то ответа нет, команда вернёт тебя в ту же
   фазу, и `prompts` перечислит только недостающие работы. Перезапусти их один раз. Если присяжный
   не справился дважды, запиши в его файл одну строку `НЕТ ГОЛОСА` (`SUD check jury` покажет недостающие
   файлы) и иди дальше. Голос, речь или решение суда сам никогда не пиши.

## Шаг 5: вердикт

Когда `SUD next` скажет, что суд окончен:

```bash
SUD render
```

Команда считает голоса, пишет `ВЕРДИКТ.md` в папку запуска и печатает его. Покажи пользователю строку
вердикта, таблицу голосов и разделы судьи ровно так, как они написаны. Потом добавь не больше двух
строк от себя: с какого одного условия оправдания ты бы начал и путь к полному протоколу суда.

Правила для тебя, секретаря суда:

- Не меняй, не смягчай и не пересчитывай вердикт. Вердикт «виновна» это полезная информация, а не
  плохая новость, которую надо подсластить.
- Не добавляй похвалы, которой присяжные не давали.
- Если пользователь не согласен с вердиктом, предложи повторный суд: условия из раздела «Условия
  оправдания» вписываются в новый файл дела. Ни за одну из сторон не заступайся.
